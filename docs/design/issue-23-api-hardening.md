## 1. 公開型から `Date` を排除する（production 変更）

### 1.1 問題

`Object.freeze` は `Date` の**内部スロットを保護しない**。`obj.date = x` は `TypeError` になるが、`obj.date.setFullYear(1999)` は通り、実値が変わる。公開結果はキャッシュ経由で共有されるため、消費側の1回の破壊的操作が以降のキャッシュヒットすべてを汚染する。#3 の検収で `recentBigLoss.startedAt.setFullYear(1999)` が例外を出さずに実値を変えることを実測している。

### 1.2 決定: `number`（エポックms）に変更し `Ms` サフィックスを付ける

| 現在 | 変更後 |
|---|---|
| `PlayerSearchResult.lastPlayedAt: Date` | `lastPlayedAtMs: number` |
| `PlayerExtendedStats.recentBigLoss.startedAt: Date` | `startedAtMs: number` |

**根拠**:

1. **number は不変**なので穴が完全に消える。getter で都度新規 `Date` を返す案も検討したが、freeze と共存する一方で仕組みが非自明でデバッグ時に惑うため不採用
2. #3 で `DATA_MIN_DATE` → `DATA_MIN_MS` + `dataMinDate()` としたのと**同じ理屈**であり、一貫する
3. `dayjs` は number（エポックms）をそのまま受け取れる（`dayjs(1618494843000)`）ため、表示側の手間は増えない
4. 単なる文書化での受け入れは不採用。設計書に書くだけでは後続Issueが規約を守る保証がなく、#3 の検収担当も推していない

### 1.3 変更箇所

| ファイル | 内容 |
|---|---|
| `src/api/types.ts` | 公開型2箇所のフィールド名と型を変更。コメントの「秒 → Date 化」も「秒 → ミリ秒」に改める |
| `src/api/normalize.ts` | `new Date(raw.latest_timestamp * 1000)` → `raw.latest_timestamp * 1000`。`最近大铳.start_time` 側も同様 |
| `src/api/normalize.test.ts` | 期待値を `Date` から number に。**期待値は `1618494843 * 1000` のように独立に計算する**こと（実装をそのまま写したトートロジーにしない。#3 の T2 が守っていた性質） |

**秒 → ミリ秒への変換自体は維持する。** ワイヤは秒、公開型はミリ秒。この境界での変換が正規化層の責務であることは変わらない。

### 1.4 設計書 [issue-3-api-layer.md](issue-3-api-layer.md) の改訂（必須）

以下を本Issueで改訂すること。

- **§4.3**: 「レスポンス内の秒単位時刻は正規化で `Date` に変換」を「**ミリ秒の number に変換し `Ms` サフィックスで単位を明示**」に改める。§4.3 の本来の目的（秒とミリ秒の取り違え防止）はサフィックスで維持される旨、および**変更の理由（freeze が Date 内部スロットを保護しないこと）**を残すこと
- **§4.3 の「公開関数の期間引数は `Date` 型のみ」は維持する。** 引数側は共有インスタンスではないため問題がなく、`getTime()` を強制することで「秒を渡してしまう」事故を型で防ぐ利点がそのまま効いている。**出力側だけを変える**という非対称性が意図的であることを明記すること
- **§4.4**: 公開型定義の該当2箇所を更新
- **§5.2**: 「既知の限界（後続 Issue で扱う production 課題）」として記載されている `Date` の段落を、**本Issueで解消済み**である旨に書き換える
- **§7.4 の T2**: 「`lastPlayedAt` が正しい `Date`」の記述を更新

### 1.5 同じクラスの穴の系統的な確認（必須）

#3 では共有可変状態の修正が**2回連続で半分に終わった**（`DATA_MIN_DATE` の返り値だけ直して export が残る / `normalize` だけ freeze して2エンドポイントが漏れる）。同じ轍を踏まないこと。

`Date` を除去したあと、**公開結果に残る可変オブジェクトが他に無いことを網羅的に確認**し、結果を報告すること。具体的には、公開7経路（`searchPlayer` / `getPlayerStats` / `getPlayerExtendedStats` / `getGlobalHistogram` / `getGlobalStatistics` / `getLevelStatistics` / `getCurrentLevel`）の戻り値を再帰的に走査し、`typeof x === 'object'` かつ freeze で守れない組み込み型（`Date` / `Map` / `Set` / `RegExp` 等）が含まれないことを確かめる。**この確認自体をテストとして残すこと**（将来 `Date` 等が再び混入したら落ちるように）。

いずれも**実装は仕様どおり**で、壊しても落ちるテストが無い箇所。#3 の検収でミューテーションテストにより特定された。既存の5テストファイルに追加し、新しいファイルは作らない。

### 2.1 テストの書き方（#3 の教訓を踏まえた必須要件）

**A: red を先に確認すること。** 各テストを追加したら、対応する実装を意図的に壊して**実際に落ちること**を確認してから完成とする。#3 でこの規律を課したことが、実効性のないテストの混入を防いだ。

**B: アサーションを緩くしないこと。** #3 では `url.includes('/result/abc123')` という部分一致のせいで、URL からAPIプレフィックスが丸ごと欠落しても通っていた。URL の検証は**期待URL全体との完全一致**で行うこと。

**C: 期待値を実装から写さないこと。** 実装の式をそのままコピーすると、実装を変えても期待値が追随してしまい何も検証しない。期待値は独立に計算するか、リテラルで書く。

**D は特に注意**: 「成功したミラーを引き継ぐ」性質を固定する必要がある。**ミラー0が落ちてミラー1で成功したケース**を作り、result の再取得先が `MIRRORS[1]` であることを完全一致で検証すること。`MIRRORS[0]` 固定にするミューテーションで落ちなければ意味がない。

**E は `hourTag()` の時刻依存に注意**: `vi.setSystemTime()` 等で時刻を固定し、異なる時刻で異なる tag が出ることを検証する。同一時間内では同じ tag になること（キャッシュが効くこと）も含めること。

**G はキャッシュ上限のテスト**: `MAX_CACHE_ENTRIES` は 500 なので、そのまま 500 件積むテストは遅い。上限値を注入可能にする production 変更は**しないこと**（本Issueはテストのみ）。代わりに、上限到達時の挙動（全クリア）が観測できる最小の方法を工夫すること。難しければ「実装が変わったら落ちる」形にできる範囲で妥協し、その旨をテストのコメントに残すこと。

## 4. 検収担当への追加指示

受け入れ条件の検証に加えて、**「まだ欠けている次元がないか」を能動的に探すこと**。

#3 で、ミューテーションテストが20/20 KILLED を達成した直後に Codex が3件の実欠陥を指摘した。原因はすべて「テストの次元の欠落」で、ミューテーションでは原理的に検出できないものだった（部分一致アサーション / 並行実行の次元の欠如 / エイリアシング）。**ミューテーションテストが保証するのは「既存のテストが実装の変更を検知できること」であって、「テストすべき次元が揃っていること」ではない。**

本Issueの9件はその反省から洗い出したものだが、**さらに残っている可能性がある**。特に次の観点で探すこと。

- アサーションが部分一致・緩い比較になっていないか
- 並行実行・エイリアシング・境界値など、実装を壊しても落ちない次元がないか
- 公開面の契約（不変性・単位・null 許容）で、テストが1方向しか見ていないものがないか

発見したものは、受け入れ条件の合否とは**分けて**報告すること。契約範囲外の発見で判定を覆さない（#3 での判断を踏襲する）。
