# UI検証の逆発注 — 運用ルール

エージェントが原理的に確認できない、あるいは確認コストが見合わないUI検証を、オーナー（人間）へ委託するための仕組み。

統括担当が `TEMPLATE.md` を複製して手順書を作り、オーナーが実行して結果欄を埋めて返す。返却された結果は検収の証跡として扱い、該当Issueの受け入れ条件の合否に反映する。

---

## 1. 逆発注する / しない の判断基準

**逆発注する**

| 類型 | 例 |
|---|---|
| エージェントの環境で再現できない | OS のダークモード設定の実切替、実機（スマホ）での表示、ブラウザペインで発火しないアニメーション完了イベント |
| ハードウェア・OS依存 | 高DPI表示でのフォントの潰れ、実際のタッチ操作、リフレッシュレート依存のモーション |
| 主観判断が本質 | 配色の印象、日本語フォントの読みやすさ、モーションの心地よさ、「LLMに作らせた感」の有無 |
| オーナーの決定事項 | デザイン方針の最終承認、叩き台からの色・文言の確定 |

**逆発注しない（エージェントが自分でやる）**

| 類型 | 理由 |
|---|---|
| DOM・CSS変数の実測値 | `getComputedStyle` で機械的に取れる。人間にやらせるのは無駄 |
| 要素の存在・サイズ | `getBoundingClientRect` で取れる |
| ビルド・lint・grep | コマンド一発 |
| コントラスト比の計算 | 数値計算。人間の目より正確 |
| 回帰確認 | 毎回人間にやらせると逆発注が形骸化する |

**原則**: 「機械で測れることは機械で測る」。人間の時間は、機械に測れないことと判断が要ることだけに使う。手順書に機械で取れる項目を混ぜないこと。

## 2. 手順書を書くときの規約

- **設計書を読まなくても実行できること**。前提知識を手順書内で完結させる
- **1ステップ1確認**。「〜を確認する」が2つ以上ある手順は分割する
- **期待結果を具体的に書く**。「正しく表示される」ではなく「バッジが赤い丸で数字の3が読める」
- **判断に迷ったときの逃げ道を用意する**。すべての項目に「判断保留」を許可し、保留理由を書ける欄を置く
- **所要時間の目安を書く**。オーナーが着手タイミングを決められるようにする
- **主観項目は「正解」を示唆しない**。「金色に見えますか？」ではなく「この色から受ける印象を書いてください」

## 3. 結果の扱い

- 「不合格」および「判断保留」は、統括担当が原因を切り分けた上で製造担当へ差し戻すか、設計判断の変更としてオーナーに諮る
- 主観項目の結果はオーナーの決定として扱い、エージェントが反論しない。ただし技術的制約と衝突する場合は制約を説明した上で再判断を仰ぐ
- 完了した手順書と結果は `docs/ui-verification/` に残す。後続Issueで同じ検証を繰り返す際の基準になる

## 4. ファイル命名

```
docs/ui-verification/
  README.md                    … 本ファイル
  TEMPLATE.md                  … 雛形
  YYYY-MM-DD-issue-N-<slug>.md … 実施分（手順書と結果を同一ファイルに残す）
```
